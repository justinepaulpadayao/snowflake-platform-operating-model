# Cortex AI Feature Governance — HIPAA / PHI Platform

**Scope:** Snowflake Cortex features available on this platform's Snowflake Enterprise account.
**Owner:** Security / Privacy Office and Data Platform leads (joint review).
**Relation to:** `ai_governance_notes.md` (general AI governance); this document provides
Cortex-specific risk profiles, controls, and approved use cases for each feature surface.

> Cortex features run entirely within the Snowflake boundary — data does not leave to
> third-party model hosts.  That makes Cortex categorically different from consumer AI tools,
> but it does not eliminate risk: PHI can still be passed to model functions in query arguments,
> model outputs can be written back to PHI schemas, and Cortex Analyst can generate SQL that
> bypasses intended row-level controls if scoped incorrectly.  Each surface below has its own
> risk profile and requires its own set of controls.

---

## Surface 1 — Cortex LLM Functions

**Functions:** `SNOWFLAKE.CORTEX.COMPLETE`, `SUMMARIZE`, `TRANSLATE`, `SENTIMENT`,
`CLASSIFY_TEXT`, `EXTRACT_ANSWER`, `EMBED_TEXT_*`

**How they work:** SQL-callable scalar functions that send the *argument value* to a Snowflake-
hosted large language model.  The argument is a VARCHAR column value, a literal string, or a
concatenated expression — whatever the caller passes.

**PHI risk:** A query such as
```sql
SELECT SNOWFLAKE.CORTEX.SUMMARIZE(clinical_notes) FROM raw_masked.gov.patient;
```
passes the *unmasked* column value to the model if the caller's session holds `AR_PHI_UNMASK`.
Cortex LLM calls appear in `QUERY_HISTORY` but the column values passed as arguments are not
stored separately — the risk is model processing of PHI, not PHI leaving Snowflake.

**Audit surface:** `SNOWFLAKE.ACCOUNT_USAGE.QUERY_HISTORY` — filter `query_text ILIKE
'%SNOWFLAKE.CORTEX.%'` to enumerate all LLM function calls.  Snowflake does not currently
provide a dedicated Cortex-specific usage view; QUERY_HISTORY is the only audit record.

| Control | Implementation |
|---|---|
| Role scoping | Cortex LLM functions may only be called by roles that hold `AR_PHI_UNMASK` if the input column is PHI. General analysts querying masked values is acceptable (masked text to the model). |
| Warehouse isolation | Assign a dedicated warehouse (`WH_CORTEX_ANALYST`) so Cortex compute is separately metered and monitored via its resource monitor. |
| Query monitoring | Add a daily check on `QUERY_HISTORY` for Cortex function calls on PHI schemas (`ILIKE 'RAW_MASKED%'` in the FROM clause of the parent query). Alert on unusual volume. |
| Output table policy | If LLM output is written back to a Snowflake table, the output table must carry a `DATA_CLASSIFICATION` tag appropriate to the input sensitivity (a summary of PHI is still PHI). |

**Approved use cases:**
- `SUMMARIZE` or `TRANSLATE` on **masked** text columns (field notes, diagnosis descriptions)
  where the caller does not hold `AR_PHI_UNMASK` — the function receives `***REDACTED***`.
- `CLASSIFY_TEXT` on de-identified or synthetic data for model development.
- `EMBED_TEXT_*` for semantic similarity on non-PHI metadata fields.

**Prohibited:**
- Passing PHI identifiers (name, MRN, SSN, DOB) directly as `COMPLETE` prompt arguments.
- Writing raw PHI + LLM-generated text into an untagged table.

## Surface 2 — Cortex Analyst

**What it is:** A natural-language-to-SQL interface backed by a semantic model (a YAML file
that maps business terms to Snowflake tables/columns).  The user asks a question in plain
English; Cortex Analyst generates and executes a SQL query.

**PHI risk:**
1. **Generated SQL may reach PHI schemas.** If the semantic model includes PHI tables, the
   generated SQL runs against those tables as the caller's role — masking and row-access
   policies still apply, but the caller may not realize they are querying PHI.
2. **Prompt injection via column values.** A malicious string in a PHI column value could
   influence the model's behavior if column samples are included in context.
3. **Generated SQL bypassing intent.** The model may generate a `JOIN` or `UNION` that
   reaches a table not intended to be in scope for the asking user.

**Audit surface:** `QUERY_HISTORY` for queries generated by the Cortex Analyst session
(identifiable by a specific `query_tag` or client application identifier set in the semantic
model configuration).

| Control | Implementation |
|---|---|
| Semantic model scoping | Include only `ANALYTICS.MARTS` and `KPIS.REPORTING` tables in the semantic model available to general analysts. PHI source tables (`RAW_MASKED.GOV`) must not appear in the analyst-facing semantic model. |
| PHI-cleared semantic model | A separate semantic model scoped to clinical analysts (role-gated) may include curated views of PHI data with masking already applied. |
| Generated SQL review | For the first 90 days after enabling Cortex Analyst, log and sample-review generated SQL weekly to confirm it does not reach out-of-scope objects. |
| Row/column policy coverage | Ensure every table in the semantic model has appropriate row-access and masking policies — Cortex Analyst queries execute as the caller's role, so all existing policies apply. |

**Approved use cases:**
- Business analysts asking metric questions over `ANALYTICS.MARTS` and `KPIS.REPORTING`.
- Platform admins querying `GOVERNANCE.ACCESS_REVIEW` for operational metrics.

**Prohibited:**
- Pointing Cortex Analyst at raw PHI schemas without PHI-cleared semantic model scoping.

## Surface 3 — Cortex Search

**What it is:** Full-text semantic search over Snowflake tables.  A search service indexes
specified columns and allows fuzzy/semantic query across them.

**PHI risk:** The search index contains sampled and encoded representations of the indexed
column values.  If PHI columns are indexed:
- PHI is stored in the search index (within Snowflake, but in a derived form).
- Search queries can retrieve PHI rows.
- The index may retain values that no longer exist in the source table (depending on
  refresh cadence).

**Audit surface:** `SNOWFLAKE.ACCOUNT_USAGE.SEARCH_OPTIMIZATION_HISTORY` and
`QUERY_HISTORY` for `SEARCH_OPTIMIZATION` query type.

| Control | Implementation |
|---|---|
| Index scope | Only index non-PHI columns (e.g., `facility_id`, `condition_category`, de-identified codes). Never index `full_name`, `mrn`, `ssn`, `email`, or `dob`. |
| Tag check before indexing | Before creating a search service on any column, verify the column has no `PII_STRING` or `PII_DATE` tag: `SELECT * FROM SNOWFLAKE.ACCOUNT_USAGE.TAG_REFERENCES WHERE COLUMN_NAME = '<col>' AND TAG_NAME IN ('PII_STRING','PII_DATE')`. |
| Access control | The search service inherits the table's masking policy — but only if the masking policy is applied. Validate with `INFORMATION_SCHEMA.POLICY_REFERENCES`. |

**Approved use cases:**
- Searching diagnosis code descriptions, facility names, and de-identified condition categories.

**Prohibited:**
- Indexing any column carrying a `PII_STRING` or `PII_DATE` tag.

## Surface 4 — Document AI

**What it is:** Processes unstructured documents (PDFs, images, scanned forms) and extracts
structured information.  Built on Snowflake's ML infrastructure.

**PHI risk:** Clinical notes, lab reports, discharge summaries, and prior-auth forms are
among the highest-sensitivity document types in a healthcare environment.  Feeding these
documents to Document AI is equivalent to querying a PHI column.

**Audit surface:** `QUERY_HISTORY` for Document AI build/predict calls.

| Control | Implementation |
|---|---|
| PHI approval gate | Any Document AI use case involving patient documents requires the same evaluation process as a new PHI-touching AI tool (`ai_governance_notes.md §1`). |
| Role enforcement | Document AI prediction must only be callable by `FR_CLINICAL_ANALYTICS` or a dedicated service role with `AR_PHI_UNMASK`. |
| Document staging | Patient documents must be staged in a Snowflake internal stage inside a managed-access schema (not an externally accessible object storage path). |
| Output classification | Extracted fields inherit the PHI classification of the source document and must be tagged and masked accordingly before any downstream use. |

**Approved use cases:**
- Pilot extraction on synthetic/de-identified documents only, until the PHI evaluation gate
  is complete and a dedicated service role is provisioned.

**Prohibited:**
- Feeding real patient documents to Document AI without completing the PHI tool evaluation,
  provisioning a purpose-built least-privilege role, and obtaining Security/Privacy sign-off.

## Surface 5 — Cortex ML Functions

**Functions:** `SNOWFLAKE.ML.FORECAST`, `ANOMALY_DETECTION`, `CLASSIFICATION`,
`TOP_INSIGHTS`, `CONTRIBUTION_EXPLORER`

**What they are:** In-Snowflake AutoML: training and inference pipelines that run entirely
on Snowflake compute against Snowflake tables.

**PHI risk:** Training on a PHI dataset bakes PHI-derived patterns into a model object.
The model object itself does not contain raw PHI, but inference outputs may indirectly reveal
PHI (e.g., a mortality forecast per patient_id that could be re-identified).

**Audit surface:** `SNOWFLAKE.ACCOUNT_USAGE.QUERY_HISTORY` for `SNOWFLAKE.ML.*` calls and
for `CREATE SNOWFLAKE.ML.FORECAST` DDL.

| Control | Implementation |
|---|---|
| Training data review | Confirm training data columns with a PHI classification review before a model is trained. Prefer training on aggregated, de-identified, or synthetic data. |
| Model object classification | Tag trained model objects (in the schema they are created) with the classification of their training data. |
| Inference output policy | Inference outputs that include patient-level predictions must be stored in a managed-access schema with appropriate masking and access controls. |
| Model access control | `CREATE SNOWFLAKE.ML.*` privilege should be granted only to `FR_CLINICAL_ANALYTICS` and `FR_PLATFORM_ADMIN`. |

**Approved use cases:**
- Forecasting aggregate admission volume, resource utilization, or de-identified cohort trends.
- Anomaly detection on platform operational metrics (warehouse credit usage, query volume).

**Prohibited:**
- Training a patient-level model on raw PHI columns without explicit Security/Privacy approval.

## Audit Queries for Cortex Usage Monitoring

```sql
-- All Cortex LLM function calls in the last 30 days.
SELECT
    user_name, role_name, start_time,
    LEFT(query_text, 400) AS query_excerpt
FROM snowflake.account_usage.query_history
WHERE start_time >= DATEADD('day', -30, CURRENT_TIMESTAMP())
  AND query_text ILIKE ANY (
      '%SNOWFLAKE.CORTEX.COMPLETE%',
      '%SNOWFLAKE.CORTEX.SUMMARIZE%',
      '%SNOWFLAKE.CORTEX.CLASSIFY_TEXT%',
      '%SNOWFLAKE.CORTEX.EXTRACT_ANSWER%',
      '%SNOWFLAKE.CORTEX.EMBED_TEXT%'
  )
ORDER BY start_time DESC;

-- Cortex ML model training calls.
SELECT user_name, role_name, start_time, query_text
FROM snowflake.account_usage.query_history
WHERE start_time >= DATEADD('day', -30, CURRENT_TIMESTAMP())
  AND query_text ILIKE ANY (
      '%SNOWFLAKE.ML.FORECAST%',
      '%SNOWFLAKE.ML.ANOMALY_DETECTION%',
      '%SNOWFLAKE.ML.CLASSIFICATION%'
  )
ORDER BY start_time DESC;

-- Any Cortex call that touches a PHI schema (join to access_history for object context).
SELECT DISTINCT
    ah.user_name,
    ah.query_start_time,
    f.value:objectName::string AS accessed_object,
    LEFT(qh.query_text, 300)   AS query_excerpt
FROM snowflake.account_usage.access_history ah
INNER JOIN snowflake.account_usage.query_history qh
    ON qh.query_id = ah.query_id
   AND qh.start_time = ah.query_start_time,
LATERAL FLATTEN(input => ah.base_objects_accessed) f
WHERE ah.query_start_time >= DATEADD('day', -30, CURRENT_TIMESTAMP())
  AND f.value:objectName::string ILIKE 'RAW_MASKED.%'
  AND qh.query_text ILIKE '%SNOWFLAKE.CORTEX.%'
ORDER BY ah.query_start_time DESC;
```
